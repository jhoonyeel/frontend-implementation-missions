# Frontend Implementation Missions

프론트엔드에서 마주치는 작은 구현 문제를 직접 분석·설계·구현·검증하며 **코드 구현 능력과 기술적 판단 역량을 훈련하는 저장소**입니다.

라이브러리와 프레임워크의 사용법을 익히는 데 그치지 않고, 필요에 따라 내부 동작을 직접 구현하면서 추상화의 목적과 한계를 이해합니다.

## 학습 목표

- 요구사항을 분석하고 필요한 상태와 데이터 흐름 설계
- JavaScript·TypeScript·React·Browser API를 활용한 직접 구현
- 비동기 처리, 사용자 상호작용, 예외 상황 및 경계 조건 검증
- 구현 방식의 선택 근거와 대안·트레이드오프 설명
- 라이브러리가 제공하는 추상화의 내부 원리 이해

## 진행 방식

**아이디어 기록 → 미션 구체화 → 직접 구현 → 검증 → 회고**

### 1. 아이디어 기록

구현해 보고 싶은 주제와 핵심 학습·검증 키워드만 기록합니다.

- [Frontend Mission Ideas](./frontend-mission-ideas.md): 프론트엔드 구현 미션 아이디어
- [Computer Systems Mission Ideas](./computer-systems-mission-ideas.md): 컴퓨터 시스템 내부 원리 관련 미션 아이디어

아이디어는 확정된 과제가 아니며, 우선순위나 진행 순서를 미리 정하지 않습니다.

### 2. 미션 구체화

실제로 진행할 주제를 선택한 뒤 AI와 함께 요구사항, 제약조건, 테스트 시나리오 및 완료 조건을 구체화합니다.

이때 **외부에서 관찰할 수 있는 동작과 문제 상황을 먼저 정의**하고, 구체적인 구현 구조나 정답 코드는 미리 결정하지 않습니다.

### 3. 직접 구현

정답 코드를 먼저 참고하기보다 스스로 문제를 분석하고 구현을 시도합니다.

구현에 막히면 필요한 개념이나 해결 단서를 학습한 뒤 다시 시도합니다. AI는 문제 이해, 개념 학습, 코드 리뷰 및 대안 검토에 활용하되 직접 구현하는 과정을 대체하지 않습니다.

### 4. 검증 및 회고

정상 동작뿐 아니라 실패·예외·경계 상황을 검증합니다.

구현 후에는 필요한 범위에서 다음 내용을 정리합니다.

- 구현 구조와 선택 이유
- 검증 결과 및 해결 과정에서 발견한 문제
- 고려한 대안과 트레이드오프
- 구현의 한계와 새롭게 이해한 개념
- 실제 라이브러리·프레임워크 동작과의 차이(해당하는 경우)

모든 항목을 매번 문서화하는 것은 목표가 아닙니다. **구현 과정에서 중요한 판단을 스스로 설명할 수 있는 상태**를 우선합니다.

## 저장소 운영

아이디어 단계에서는 별도의 미션 디렉터리를 생성하지 않습니다.

실제 미션을 시작할 때 독립적인 작업 공간을 만들고, 구현 코드와 필요한 문서를 함께 관리합니다.

```text
frontend-implementation-missions/
├── README.md
├── mission-ideas.md
├── computer-systems-missions.md
└── missions/                  # 실제 미션 진행 시 생성
    └── <mission-name>/
        ├── README.md          # 요구사항·검증 기준
        ├── src/               # 구현 코드
        └── retrospective.md   # 필요시 회고
```

위 미션 디렉터리는 예시이며, 파일 구성은 미션 성격에 따라 조정할 수 있습니다.

## 완료 기준

미션의 완료 여부는 코드 실행뿐 아니라 다음 질문에 답할 수 있는지를 기준으로 판단합니다.

1. 어떤 문제를 해결했는가?
2. 어떻게 구현했고, 왜 그 방식을 선택했는가?
3. 정상·예외 상황에서 기대한 대로 동작하는가?
4. 현재 구현의 한계와 다른 대안은 무엇인가?

내부 동작을 직접 구현하는 미션에서는 **해당 추상화가 왜 필요하며, 실제 라이브러리는 무엇을 추가로 고려하는지**까지 비교합니다.
